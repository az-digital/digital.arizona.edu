The header above is the current release. It matches this page except for keyboard focus on
the header buttons: they draw the ring every button gets, 2px outside the button, instead
of the header's ring inside their edges. On a site, header buttons only show below 992px.

## Colors

- **Blue** (default): the current, recommended header color.
- **Red**: the original header color. It's being retired, so don't use it for new sites.

## Design decisions

The header's contract (`brand-header.contract.json`) sets each of its parts' design
properties: its colors are brand colors, its focus ring width is the shared one, its
spacing comes from the spacing scale where a step matches, and its other sizes and its
timings are the header's own values, written in the contract. The header has no design
tokens of its own.

- **Fill:** <Token data={getTokenData('az.color.brand.blue')} />. The original red header
  isn't a separate set of design tokens: its contract points the fill at Red, and keeps every
  other color White. The red header is only needed until it's retired.
- **Size:** the header is at least 50px tall, and exactly 50px below 992px. The wordmark
  fits a 211 × 16px box below 576px and a 266.41 × 19.8px box from 576px up, 10px from
  the header's left edge. It keeps its own proportions inside that box, so it's 211px
  and 266.41px wide and a little shorter than the box.
- **Keyboard focus:** the logo and header buttons draw a ring inside their edges, with
  2px corners, in <Token data={getTokenData('az.color.fg.white')} />. Its width is the
  shared focus ring width, <Token data={getTokenData('az.focus-ring.width.md')} /> (2px).
- **Header buttons** (for adding search and menu toggles on mobile): at least 60px
  wide and as tall as the header, with <Token data={getTokenData('az.spacing.050')} /> (4px)
  of padding above and below.
  - **Label:** text in <Token data={getTokenData('az.color.fg.white')} />, 10px with a
    10px line height, <Token data={getTokenData('az.spacing.025')} /> (2px) below the icon.
  - **Icon:** 24px square, the same color as the label. Use an SVG (inline or from a
    sprite) with `fill="currentColor"` so it picks up that color.
- **Logo:** the university's white wordmark,
  <Token data={getTokenData('az.color.fg.white')} />, on both the Blue and the Red header.
  It's a registered university mark, so use the official file as it is: don't recolor,
  stretch, crop or redraw it, or add effects such as shadows. Use the wordmark header
  only on a page that also shows a Block "A" logo, usually in the site's branding just
  below the header. The <a href="https://marcom.arizona.edu/brand-guidelines/logos" target="_blank" rel="noopener noreferrer">university's logo guidelines</a>
  cover the rest.
- **Motion:** the off-canvas panel the header buttons open slides in over 300ms,
  ease-in-out, and the backdrop behind it fades in over 150ms. Header buttons change
  color and show their focus ring over 150ms. They haven't been
  reviewed by design yet, and all of them turn off when someone asks for reduced
  motion.
- **Fixed on mobile:** when the header is pinned to the top of the screen below 992px,
  linked sections stop <Token data={getTokenData('az.spacing.100')} /> (8px) below the
  header when scrolled to (58px from the top), so the header doesn't cover them.

## When to use it

- **Use it** for one thing to do, such as subscribing to a newsletter or registering for
  an event.
- **Write the button as the action,** in a word or two: "Subscribe", "Register".
- **One button per card.** For several links, use a

- **Button:** a default size Red

  32px below the text.

- **Title:** 22px Bold, on a 30px line, in

# Card

A title and any content in a Cloud box, to read where it is. It isn't a link.

<Canvas of={CardStories.Default} sourceState="hidden" />

<Controls of={CardStories.Default} />

The card above is Arizona Bootstrap v5.3.0. Its `.card-body` is the slot: the
title, then Body, written as HTML here and as the editor's rich text in a site. Type a
header or footer to add one.

Arizona Bootstrap gives a Cloud card its title and text colors only when the whole card is a link, so this card sets them with `.text-azurite` on its title and `.text-tinta` on its body.

## When to use it

- **Use it** for content that's complete on the card, such as office hours or a short
  notice.
- **Its body is a slot:** paragraphs, a list or a small table, all in the card's text
  type. It's the only card with one. Keep it short; for a whole section, use the page.
- **Don't put links or buttons in the body to make a different card:** use a
  <a href="./?path=/docs/primary-components-containers-cards-quick-links-card--docs" target="_top">Quick Links Card</a>
  or a
  <a href="./?path=/docs/primary-components-containers-cards-call-to-action-card--docs" target="_top">Call to Action Card</a>.
- **It's the only card with a header and footer,** for a label above the content or a
  note below it.
- **If the card should go to a page,** use a
  <a href="./?path=/docs/primary-components-containers-cards-link-card--docs" target="_top">Link Card</a>
  instead.

## Design decisions

- **Fill:** <Token data={getTokenData('az.color.bg.card.cloud')} />, with no border: the
  fill sets the card apart from the page. In a forced colors (high contrast) mode, which
  removes fills, the card draws a 1px border instead.
- **Shape:** 16px corners.
- **Padding:** 24px between the card's edges and its content. The header and footer have
  24px to the left and right, so their text lines up with the body's, and 12px above and
  below.
- **Title:** 22px Bold, on a 30px line, in
  <Token data={getTokenData('az.color.brand.azurite')} />. 8px below the title's line.
- **Body:** 18px Regular, on a 28px line, in
  <Token data={getTokenData('az.color.brand.tinta')} />: the same size as body text, for
  everything in the slot. 16px between blocks, such as a paragraph and a list.

# Grid

Pages use a 12-column grid inside a centered container. The gutter is 24px between columns (12px on each side of a column), the same as `az.spacing.300`. Containers have 12px of padding on each side, half the gutter; that padding is derived from the gutter, so it has no separate token.

The maximum container width changes at each breakpoint. Below `sm`, it stays fluid; from `sm` up, each breakpoint sets a maximum width.

The column count, gutter and container widths follow the current implementation (5.2.2).

## When to use it

- **Use it** in a row of cards that each go to a part of the site, such as Future
  Students, Current Students and Alumni, where an icon helps people find theirs.
- **Pick an icon for the page, not for decoration.** Screen readers skip it, so the title
  has to say everything on its own.
- **Use icon cards together:** in a row, give every card an icon, or none.
- **Don't put a button or other links in it:** the whole card is already one link.

## Design decisions

- **Icon:** 60px, in <Token data={getTokenData('az.color.brand.azurite')} />, with 16px
  between it and the title's line. Use an icon font glyph at that font size, or an SVG at
  that width and height with `fill="currentColor"`. The icon is decorative, so hide it
  from screen readers with `aria-hidden="true"`.
- **Fill:** <Token data={getTokenData('az.color.bg.card.cloud')} />, with no border. In a
  forced colors (high contrast) mode, which removes fills, the card draws a 1px border
  instead.
- **Title:** 22px Bold, on a 30px line, in
  <Token data={getTokenData('az.color.brand.azurite')} />. 8px below the title's line.
- **Text:** 18px Regular, on a 28px line, in
  <Token data={getTokenData('az.color.brand.tinta')} />.
- **Shape and padding:** 16px corners, and 24px between the card's edges and its content.
- **Hover:** the fill turns <Token data={getTokenData('az.color.bg.card.cloud-hover')} />,
  the text turns <Token data={getTokenData('az.color.brand.white')} />, and the icon and
  title turn <Token data={getTokenData('az.color.brand.rain')} />. The title is
  underlined.
- **Keyboard focus:** when <kbd>Tab</kbd> reaches the title link, the card shows its hover
  colors, and the link's ring is Rain. Its width is the shared
  <Token data={getTokenData('az.focus-ring.width.md')} /> (2px).
- **Touch screens:** on a device that can't hover, such as a phone, the title is always
  underlined.
- **Motion:** the colors fade over 300ms, ease-out. The fade turns off when someone asks
  for reduced motion; the colors still change.

# Alt text guidance

## What is alt text?

Alternative text (alt text) is a written description that helps make images understandable to people who cannot see them. Alt text serves as a text alternative for images and plays an important role in making websites accessible to everyone.

Alt text serves a few important purposes:

- **Screen readers:** Screen readers and other assistive technologies use alt text to communicate the meaning or purpose of images. [Listen to an example of screen readers reading images with and without alt text.](https://www.youtube.com/watch?v=NvqasTVoW98)
- **Images that don't load:** Alt text can appear in place of an image if it fails to load, benefiting all users.
- **Search engines:** Alt text helps search engines understand image content and can improve search results.

## How to use this guide

Not every image needs the same type of alt text. The appropriate approach depends on the image's purpose and context on the page.

Learn how to write accurate and meaningful alt text for different types of images, including photos, logos, icons, SVGs, charts, diagrams, and images of text. This guidance focuses on still images and does not cover video or audio alternatives.

## Start with the image’s purpose

An image’s alternative communicates what the image contributes to the page, not everything that can be seen in it. The same image can need a different alternative in a different context.

- **Informative images** convey information that is not available in nearby text. Describe the relevant information, not just the fact that an image is present.
- **Decorative or redundant images** add no information beyond nearby text or are included only for visual appeal. Use an empty alt attribute (`alt=""`) so assistive technology can skip them. An empty alt attribute is intentional. Omitting the `alt` attribute entirely can cause screen readers to announce the image's file name instead, which can be confusing for users.
- **Functional images** act as links or controls. Describe the action or destination when the image is the only label. When visible text already gives the link or control its accessible name, avoid repeating it in the image alternative.
- **Complex images** (such as charts, maps, and diagrams) need:
   - A concise alternative identifying their subject or takeaway.
   - A nearby or linked text explanation of the essential details (such as a data table).

Use real, selectable text instead of an image of text. If an image of text is necessary, make the same wording available as text and provide an alternative that conveys its purpose. There is no single character limit that works for every image; be concise, but include the essential information and context.

## Guidance for common components

- **Cards:** If the image is decorative or the card’s visible title and link already convey its purpose, use `alt=""`. If it adds distinct information, describe that contribution without repeating the card title.
- **Hero and banner images:** Use an alternative only for information the image adds beyond the page heading and nearby copy. Avoid generic phrases such as “hero image” or “banner.”
- **Headshots and profile images:** When the person’s identity matters and is not already stated nearby, use their name. If a visible name already identifies the person, the portrait is often redundant and can use `alt=""`.
- **Arizona logos:** Describe the logo’s purpose in context. For a logo that is the only content in a link to the University of Arizona home page, use an alternative such as “University of Arizona home.” If the link also includes the university’s name as visible text, the logo is redundant; use `alt=""` for it. Follow the approved brand name and avoid repeating nearby text.

Assess redundancy for each image in its actual context; the same image may be informative in one place and decorative in another. When a single stored alt text is reused across pages, write it so it is accurate everywhere the image appears.

## Icons, SVGs, and background images

- A meaningful CSS background image cannot have an `alt` attribute. Put essential information in visible text or another text alternative in the page rather than making CSS the only way to access it.
- Hide decorative icons from assistive technology (for example, with `aria-hidden="true"`). An icon is decorative when nearby text already says the same thing, such as a phone icon next to a link that shows the phone number. An icon-only button or link still needs an accessible name that describes its action or destination; do not rely on the icon’s appearance alone.
- Give a meaningful inline SVG an accessible name and appropriate image semantics, such as a `<title>` referenced by `aria-labelledby` with `role="img"`. If the SVG is decorative, hide it from assistive technology instead. Ensure its text alternative is available to users of the supported implementation.

## Responsibilities

- **Designers:** In Figma handoffs, identify whether each image is informative, functional, or decorative and propose its description in context. Call out visible text that makes an image redundant, and flag complex images that need a longer explanation or data.
- **Developers:** Preserve image descriptions through HTML, React, and web component implementations. Set the `alt` property on image elements; use `alt=""` for decorative images. Ensure component APIs pass that value through, and provide accessible names for icon-only controls. Do not put essential information only in CSS backgrounds.
- **Content editors:** When adding media in Drupal or Arizona Quickstart, enter alt text in the media’s alternative-text field when the image conveys information. Leave it empty for decorative or redundant images when the editor supports an empty alternative. Review descriptions in the page where the media is used; do not use captions, filenames, or image titles as substitutes.
- **Everyone:** The examples in this guide are starting points, not text to reuse without checking the image and its context. Any suggested or generated image descriptions must be reviewed for accuracy and purpose.

For editorial language beyond image descriptions, see the [Style guide for writing](?path=/docs/primary-foundations-content-design-style-guide-for-writing--docs).

# Designing

Accessibility is part of the design process, not a final check. Make inclusive decisions during discovery, design, prototyping, review, and handoff; changing a pattern before it is built is usually less costly than retrofitting it.

Use **WCAG 2.1 Level AA as the minimum conformance target** identified by [University of Arizona Digital Accessibility](https://accessibility.arizona.edu/). Where practical, account for relevant WCAG 2.2 additions, including **Target Size (Minimum)** and **Focus Not Obscured (Minimum)**; they are Level AA criteria in WCAG 2.2, not part of the WCAG 2.1 baseline.

## Structure and reading order

Plan a clear content hierarchy that remains understandable when the layout changes.

- Establish a logical heading outline; use headings to describe sections, not just to style text.
- Arrange content in a meaningful reading and keyboard order, even when visual layout uses columns or cards.
- Show how labels, instructions, controls, and supporting content relate to one another.
- Check that rearranging or stacking content at narrow widths does not change its intended meaning.

## Color and visual communication

Choose combinations and states that remain perceivable without relying on color alone.

- Meet WCAG contrast minimums: 4.5:1 for normal text, 3:1 for large text, and 3:1 for meaningful graphical objects and UI component boundaries or states.
- Pair color with another cue, such as text, an icon, a shape, or a pattern, to communicate selected, error, warning, or success states.
- Make interactive, selected, error, warning, and disabled states distinguishable; do not use color as the only difference.
- Review important content and controls in high-contrast and reduced-color conditions, and check focus indicators against adjacent colors.
- Start with documented Arizona Digital components and design tokens where available. A brand color token alone does not guarantee an accessible color pairing; verify the foreground and background together. See <a href="./?path=/docs/primary-foundations-tokens-how-to-use--docs" target="_top">How to use Arizona Digital design tokens</a>.

## Typography

Use the design system's type scale to support comfortable reading at different sizes.

- Choose readable type sizes and line spacing; avoid relying on very small text for essential information.
- Prefer live, selectable text over text embedded in images.
- Check longer passages and controls at enlarged text sizes to catch clipping, overlap, or lost content.
- For link text, instructions, and editorial choices, follow <a href="./?path=/docs/primary-foundations-accessibility-writing-text--docs" target="_top">Writing &amp; Text guidance</a> and the <a href="./?path=/docs/primary-foundations-content-design-style-guide-for-writing--docs" target="_top">Style guide for writing</a>.

## Interaction and keyboard behavior

Describe the interaction, not just its appearance, so keyboard behavior can be implemented and reviewed.

- Define a logical focus order and a visible focus treatment for each interactive control.
- Keep focused items visible; consider sticky headers, banners, dialogs, and overlays that may cover them. WCAG 2.2 adds the AA criterion Focus Not Obscured (Minimum).
- Specify expected keyboard interactions, including how users move through and activate controls.
- For dialogs, menus, and other temporary interfaces, note where focus starts, how users leave or dismiss the interface, and where focus returns.
- Provide alternatives to hover-only, dragging, or precise pointer interactions.

## Forms, errors, and feedback

Make it clear what information is needed, what went wrong, and what happens next.

- Show persistent labels for fields; do not use placeholder text as the only label.
- Place instructions before users need them, and make required fields clear in text as well as visually.
- Identify errors specifically, associate them with the affected field, and explain how to correct them.
- Define success, warning, loading, and status messages, including when and where they appear.
- Use more than color to distinguish a state or message. Note in handoff when updates need to be announced to assistive technology.

## Motion and media

Design media and movement so they do not create unnecessary barriers or distraction.

- Avoid unnecessary animation and provide a reduced-motion alternative when motion is not essential.
- Give users control over moving, blinking, or automatically updating content when required by WCAG.
- Plan for captions and transcripts for audio or video, and audio descriptions when important visual information is not conveyed in the soundtrack.
- Link image decisions to <a href="./?path=/docs/primary-foundations-accessibility-alt-text-guidance--docs" target="_top">Alt text guidance</a> rather than putting essential text in an image.

## Responsive design, zoom, and reflow

Layouts should adapt to user settings and content, not only to a fixed set of device mockups.

- Review narrow layouts at 320 CSS pixels and at 200% browser zoom; preserve content and functionality without unnecessary two-direction scrolling.
- Allow text enlargement and longer labels, translated content, and user-generated content without clipping or overlap.
- Keep controls usable when content reflows, and ensure the visual order still matches the meaningful reading order.
- For WCAG 2.2 readiness, design touch targets at least 24 by 24 CSS pixels or provide the spacing required by Target Size (Minimum), subject to the criterion's exceptions.

## Design annotations and developer handoff

Design specifies intended meaning and behavior; implementation and testing confirm that the interface works with assistive technology and meets the target.

Include the following in handoff when relevant:

- Semantic intent, such as whether an element is a button or a link, and which regions are landmarks.
- Heading structure, accessible names, descriptions, and relationships between controls and instructions.
- Focus order, focus management, keyboard interactions, and behavior when a dialog or menu opens and closes.
- Component states, required-field treatment, error recovery, and status feedback.
- Content alternatives for images and media, including links to the relevant <a href="./?path=/docs/primary-foundations-accessibility-alt-text-guidance--docs" target="_top">Alt text guidance</a>.

Developers are responsible for implementing semantic markup, keyboard and assistive-technology behavior, and programmatic status announcements. Designers should provide the intended content, states, and interaction behavior; teams should review the result together.

## Design review checklist

- Does the content have a logical hierarchy and reading order?
- Do text, meaningful icons, controls, and focus indicators have sufficient contrast?
- Is meaning communicated by more than color, and are all important states distinguishable?
- Can users understand and operate each interaction with a keyboard?
- Are form labels, instructions, errors, and feedback clear and complete?
- Does the layout work with enlarged text, at narrow widths, and with long or translated content?
- Are motion and media alternatives planned, and are accessibility expectations captured in handoff?

# Style guide for writing

Use this guide to make University of Arizona web content clear, useful, and accessible. It summarizes practical recommendations; it does not replace official university editorial standards or a full accessibility review.

University-wide naming, capitalization, dates, and punctuation conventions come from [MarCom’s Written Style Guide](https://marcom.arizona.edu/communications/written-style-guide). The web writing practices below apply to digital content. Examples are illustrative, not additional university rules. The [Libraries Content Style Guide](https://lib.arizona.edu/help/employees/style-guide) and [Content Principles](https://lib.arizona.edu/help/employees/content) are department-specific guidance for University Libraries; use them as examples, not as university-wide policy. If sources conflict or do not answer a question, ask your unit’s communications or content lead rather than inventing a rule.

## 1. Write for your audience

- Identify who needs the page and what they came to do. Write for that audience’s needs, not for the organization’s internal structure.
- Give the page one clear purpose. Put the answer, deadline, eligibility, or next step near the beginning.
- Include only details that help readers complete their task; link to supporting information when it belongs elsewhere.

**Example**

Before: “Our office provides a range of services related to financial support for students.”

After: “Find scholarships, grants, and other ways to pay for college.”

The revised sentence names the reader’s task and the information they can find. See the Libraries’ department-specific [Content Principles](https://lib.arizona.edu/help/employees/content) for more examples.

## 2. Make content easy to scan

- Use headings that describe the information below them; organize sections in the order readers need them.
- Use heading levels in sequence to show structure. Do not choose a heading level just to change its appearance.
- Keep paragraphs focused and concise. Use numbered lists for steps and bulleted lists for related items.

**Example**

Before: “More information”

After: “Eligibility requirements for graduate applicants”

The revised heading previews the section’s content. On a web page, format it as the appropriate heading level, not merely as bold text. See [Heading Structure Fundamentals](https://accessibility.arizona.edu/web-apps/heading-structure) and Storybook’s [Accessibility](?path=/docs/primary-foundations-accessibility--docs) guidance.

## 3. Write clearly and accessibly

- Prefer familiar, specific words and active voice. Address readers directly when that makes instructions easier to follow.
- Give one clear action per instruction. State what to do, what is needed, and when or where to do it.
- Explain necessary technical or university-specific terms on first use. Avoid idioms, jargon, and culturally specific expressions that may not translate clearly.

**Example**

Before: “In order to complete the application, it is necessary for you to submit all required documentation by the deadline.”

After: “Submit all required documents by the deadline to complete your application.”

Use plain language without removing information readers need. See Storybook’s [Writing & Text](?path=/docs/primary-foundations-accessibility-writing-text--docs) guidance. For images, see [Alt text guidance](?path=/docs/primary-foundations-accessibility-alt-text-guidance--docs).

## 4. Make links and actions meaningful

- Write link text that makes sense out of context and describes the destination or action. Avoid “click here,” “read more,” or a bare URL.
- Label buttons with the action they perform, such as “Submit application” or “View account.”
- Identify a file’s format when it helps people decide whether to download it; include the format in the link text, for example “Download the application guide (PDF).”

**Example**

Before: “For application deadlines, click here.”

After: “Review application deadlines.”

Link the revised text to the deadlines page. See [Writing Meaningful Link Text](https://accessibility.arizona.edu/documents-media/meaningful-links) and Storybook’s [Writing & Text](?path=/docs/primary-foundations-accessibility-writing-text--docs) guidance.

## 5. Use Arizona’s voice and editorial conventions

- MarCom describes Arizona’s brand voice with five traits: compassionate, confident, curious, determined, and optimistic. Use these traits as a foundation, not as a requirement to make every page sound the same.
- Match tone to the page’s purpose and audience. Service and instructional content should prioritize clear, helpful information; recruitment and fundraising content may appropriately be more promotional.
- Follow MarCom’s official conventions for the university’s name, capitalization, dates, punctuation, and other editorial details. Do not treat a department’s local style as university-wide policy.

For voice principles, see [MarCom Voice & Tone](https://marcom.arizona.edu/brand-guidelines/voice-tone). For institutional editorial conventions, see the [MarCom Written Style Guide](https://marcom.arizona.edu/communications/written-style-guide). University Libraries’ [Content Style Guide](https://lib.arizona.edu/help/employees/style-guide) is an additional department-specific reference, not a substitute for MarCom’s university-wide guidance.

**Example**

For a service page:

Before: “We are thrilled to announce a comprehensive and unparalleled student resource!”

After: “Find resources to help you plan your next steps.”

The revised service copy stays welcoming while foregrounding what readers can do. For recruitment or fundraising, a more promotional tone may fit the purpose; keep claims accurate and follow MarCom’s [Voice & Tone](https://marcom.arizona.edu/brand-guidelines/voice-tone) guidance.

## 6. Review before publishing

Before publishing, confirm:

- **Accuracy:** Names, dates, requirements, links, and contact details are current and verified.
- **Purpose and clarity:** The page serves a defined audience task; the main point and next step are easy to find.
- **Structure:** Headings describe their sections and follow a logical heading order; paragraphs and lists are easy to scan.
- **Links and actions:** Link and button labels explain what happens; file formats are identified where useful.
- **Editorial consistency:** University-wide conventions follow MarCom guidance. Any department-specific guidance is clearly scoped.
- **Accessibility:** Content works with assistive technology and supports accessible use; related images have appropriate text alternatives.

A writing review alone does not establish that a page or its documents are fully accessible. Before publishing, work through the university’s [Accessibility Tools & Checklists](https://accessibility.arizona.edu/tools-checklists), which include the WCAG 2.2 AA checklist for web pages and quick checks for documents and media. For related design system guidance, see Storybook’s [Accessibility](?path=/docs/primary-foundations-accessibility--docs) pages.

# Naming Design Tokens

Every token name is built from the same set of parts, so you can tell what a token is for by reading its name, and guess a token's name before you look it up. The same name is used in Figma, in `tokens.json`, and in the CSS, Sass and JavaScript outputs.

## Structure

<code>[namespace].[category].[property].[component/context].[variant]-[state].[size]</code>

Only the namespace and category are required. Leave out any part that doesn't apply, but keep the rest in this order.

<table>
  <tbody>
    <tr><th>Part</th><th>What it is</th><th>Examples</th></tr>
    <tr><td>namespace</td><td>Always <code>az</code>.</td><td><code>az</code></td></tr>
    <tr><td>category</td><td>The kind of value.</td><td><code>color</code>, <code>spacing</code>, <code>radius</code>, <code>border</code>, <code>opacity</code>, <code>font-size</code>, <code>breakpoint</code></td></tr>
    <tr><td>property</td><td>Which part of the category, when it has more than one.</td><td><code>bg</code>, <code>fg</code>, <code>width</code></td></tr>
    <tr><td>component/context</td><td>Where the token is meant to be used. A component name such as <code>button</code> also covers anything that behaves like one: icon buttons, pagination, list items, navigation. ## Rules

- **Don't repeat a word.** If a part already says it, the next part doesn't say it again: `az.spacing.100`, not `az.spacing.spacing-100`; `az.color.bg.button.red`, not `az.color.bg.bg-button-red`.
- **Join a state to the part before it.** A state is written after a hyphen, not as its own part, and the resting value has none: `az.color.bg.button.red`, `az.color.bg.button.red-hover`, `az.opacity.button-disabled`. That keeps `red` a single token; it couldn't also be the start of `red.hover`.
- **Use lowercase words or numbers.** Join words inside one part with a hyphen: `arroyo-blue`.
- **Shared decisions take Bootstrap 6's name.** A decision many components share, such as the focus ring or a border, is named the way Bootstrap 6 names it, with Arizona's value and a size step: `az.focus-ring.width.md` for `--focus-ring-width`, `az.border.width.sm` and `.md` for `--border-width`.
- **No role names yet.** Don't name tokens after roles such as `primary` or `accent`. Red and Blue are both primary colors, and which role each one plays hasn't been decided.
- **Prefer a component or context name over a one-off.** A token named for `button` can be used by anything button-like, so you don't need a new token for each component.

In Figma, the **AZ** variable collection stands for the `az` namespace, so a variable's path is the token name without `az`. Each output writes the same name its own way.

# Contributing Token Changes

## Summary

The currently supported contribution workflow uses Tokens Studio for Figma to publish token changes and pull approved repository updates back into Figma.

## Source of truth

- **Canonical file:** `packages/tokens/tokens.json`
- **Sync mode:** single-file sync mode in Token Studio
- **Format:** write `tokens.json` the way Tokens Studio reads it. References leave out the `az` token set (`{color.brand.red}`, not `{az.color.brand.red}`), sizes are strings (`"8px"`), and font families are one comma-separated string. Tokens Studio shows DTCG 2025.10 size objects and font lists as raw JSON, and can't resolve a reference that includes the set name.
- **Generated output:** `packages/tokens/dist/tokens.json` is generated and must not be edited in Figma

## Branch policy

Configure **main** as the sync provider's base branch. For each token update, use Token Studio to create a new issue branch, push the change to that branch, and open a pull request back to **main**. Do not push token edits directly to **main**.

## Before you start

- **<a href="https://www.figma.com" target="_blank" rel="noreferrer">Figma</a> account** — with edit access to the file you're working in. An <a href="https://www.figma.com/education/" target="_blank" rel="noreferrer">EDU account</a> works fine.
- **GitHub account** — added to the <a href="https://github.com/orgs/az-digital/teams/developers" target="_blank" rel="noreferrer">Arizona Digital developers team</a>. Install the <a href="https://github.com/mobile" target="_blank" rel="noreferrer">GitHub mobile app</a> for multi-factor authentication.
- **<a href="https://www.figma.com/community/plugin/843461159747178978/tokens-studio-for-figma" target="_blank" rel="noreferrer">Tokens Studio for Figma</a> plugin** — a non-pro account is sufficient.
- **A password saving utility** (recommended) — for saving your GitHub PAT so it's easy to re-enter or share between the Figma desktop and web apps. NetID holders can use <a href="https://stache.arizona.edu/" target="_blank" rel="noreferrer">Stache</a>, or use any password manager you prefer.

## Setup

**Supported plugin: Tokens Studio for Figma** — these instructions apply to Tokens Studio. Follow the <a href="https://docs.tokens.studio/get-started/install-figma-plugin" target="_blank" rel="noreferrer">official plugin installation guide</a> before continuing. Other supported Figma plugins will have their own setup instructions.

### 1. Create a fine-grained PAT

1. Open GitHub account settings and select **Credentials**.
2. Create a fine-grained personal access token.
3. Set the token expiration to no more than one year.
4. Set the resource owner to `az-digital`.
5. Choose **Only select repositories** and select `az-digital/design`.
6. Set **Contents** to **Read and write**.
7. Leave the required **Metadata** permission as **Read-only**.

See GitHub's <a href="https://docs.github.com/en/authentication/keeping-your-account-and-data-secure/managing-your-personal-access-tokens" target="_blank" rel="noreferrer">personal access token guide</a> for creation, storage, rotation, and revocation details.

Save the PAT in <a href="https://stache.arizona.edu/" target="_blank" rel="noreferrer">Stache</a> so it's easy to re-enter if you need to set up the sync provider again on another machine, or share it between the Figma desktop and web apps.

### 2. Add the sync provider

1. In Token Studio, open **Settings**.
2. Under **Sync providers**, select **Add new sync provider** and choose GitHub.
3. Enter the PAT and the provider settings below.
4. Save the provider, then select **Apply** so it becomes active.

See Tokens Studio's <a href="https://docs.tokens.studio/token-storage/manage-sync-provider/" target="_blank" rel="noreferrer">sync provider guide</a> for the current plugin interface and provider management options.

## Publish from Figma to repo

1. Pull the latest tokens from `main` before editing.
2. Update tokens in Figma and check their names against <a href="./?path=/docs/primary-foundations-tokens-naming--docs" target="_top">Naming</a> and their aliasing.
3. Create a new branch in Token Studio using the issue number and a short description, for example `issue-5-token-update`.
4. Push changes from Token Studio to that issue branch.
5. Open a pull request from the issue branch into `main`.
6. Use the generated Storybook review site to inspect token output before approval.
7. Merge after review and approval.
8. Build token output to regenerate consumer artifacts.

## Pull from repo to Figma

1. Open the Figma file with Token Studio enabled.
2. Configure the GitHub provider to use `main`.
3. Pull the latest repo updates from `main`.
4. Review any name or alias changes before applying them in the design file.
5. Update layers to use the new tokens rather than hard-coded values.

## Export to Figma variables

`tokens.json` defines one theme, **Mode 1** in the **AZ** group, which enables the `az` token set. Exporting it creates an **AZ** variable collection with a single **Mode 1** mode, the same name Figma gives a new collection's first mode.

Themes are a Tokens Studio Pro feature, so what you get depends on your plan:

- **Pro:** in **Export styles & variables to Figma**, choose **Themes** and select **AZ / Mode 1**. No extra mode is added.
- **Free:** you can only export by token set, and Tokens Studio names both the collection and the mode after the set, `az`. Either keep `az` as the mode name, or after each export rename the `az` mode to **Mode 1** and delete the leftover empty mode.

## Designer usage guidance

- Use semantic tokens for production-facing design decisions such as surfaces, borders, and text.
- Use base tokens only for token creation and audits, not for direct production UI assignments.
- Apply tokens through Token Studio bindings so values stay tied to names instead of hardcoded hex values.
- In a component, bind each part's colors and shared decisions to the tokens its contract lists (the Anatomy table on its docs page), and use the contract's values for its sizes and timings. Components don't have tokens of their own.

## Governance

Before merging changes, confirm the scope, review token impacts in Storybook, validate naming (see <a href="./?path=/docs/primary-foundations-tokens-naming--docs" target="_top">Naming</a>) and alias structure, and obtain approval from the appropriate reviewers.

Request review from the <a href="https://github.com/orgs/az-digital/teams/developers" target="_blank" rel="noreferrer">Arizona Digital developers team</a>. **Arizona Digital Admins must approve all token changes before merge.** A token change is not canonical until its pull request is approved and merged.

## Troubleshooting

Start with Tokens Studio's <a href="https://docs.tokens.studio/token-storage/troubleshooting-common-sync-provider-errors" target="_blank" rel="noreferrer">common sync provider errors guide</a>.

- If sync fails, verify the PAT, repo name, branch, and storage location.
- If tokens appear stale in Figma, confirm the repo branch is current and the token file is the canonical source.
- If values drift, check for direct edits outside the repository token source and regenerate outputs as needed.

# Contributing Components

Use this workflow for every component, regardless of its implementation library. The package READMEs linked from <a href="./?path=/docs/primary-components-overview--docs" target="_top">Components → Overview</a> provide platform-specific setup and verification.

## Component workflow

### 1. Propose the component

Open an issue in [az-digital/design](https://github.com/az-digital/design/issues) describing the need, users, context, and desired behavior. Link any existing product example or design. Repository maintainers confirm the scope, intended audiences, and which implementation(s) are appropriate before implementation begins.

### 2. Agree on design decisions

Determine which source settles each design decision; different decisions may have different sources. Link approved Figma frames and other relevant sources from the issue and Storybook docs, and record them in the component contract's `sources`. If sources conflict and no recorded decision resolves it, ask maintainers before choosing. Contributors who need Figma access should follow the guidance tracked in [issue #66](https://github.com/az-digital/design/issues/66); that issue is the source for the access page once it is published.

### 3. Record the contract and tokens

Record the component's anatomy, variants, design properties, and sources in `packages/contracts/contracts/<name>.contract.json`. Reuse design tokens for colors and shared decisions when they express the same design choice; add or change a token only when the decision belongs in the shared token system. Keep values specific to one component, such as its sizes and timings, in the contract rather than creating `az.component.*` tokens. Follow <a href="./?path=/docs/primary-foundations-tokens-naming--docs" target="_top">Tokens → Naming</a> for token names and <a href="./?path=/docs/primary-foundations-tokens-contributing--docs" target="_top">Tokens → Contributing</a> for token authoring and build steps. See the <a href="https://github.com/az-digital/design/blob/main/packages/contracts/README.md" target="_top">contracts guide</a> for the contract format and validation.

### 4. Select implementations

Not every component needs an implementation in every library. The issue owner and maintainers decide the required implementations based on the component's users and target platforms. Shipping one implementation is appropriate when it meets the approved need and the other platforms are out of scope; record that decision and any missing implementations in the issue or component docs.

Keep behavior and shared story args aligned across the implementations that are in scope. Adapt prop naming where a platform requires it, and document any difference rather than pretending the APIs are identical.

### 5. Add the Storybook story

Add one story file for the component, spreading `componentStories` into its meta and tagging it with each library in scope (`lib:html`, `lib:web`). Use shared args to compare implementations, and ensure the **Code** panel shows the actual source users need for the selected implementation (HTML, JSX or custom-element markup). Link the story to the relevant design source, such as its Figma frame; use the design integration proposed in [issue #13](https://github.com/az-digital/design/issues/13) when available, or a direct link until then.

### 6. Review and verify

Open a pull request with the issue and design-source links. Run the relevant package checks and Storybook tests/build, share the Storybook preview, and ask reviewers to verify the target platform as well as the Storybook rendering. Check semantic HTML, keyboard operation, focus visibility, accessible names, contrast, responsive behavior, and relevant automated accessibility checks.

## Component definition of done

- [ ] The component request and scope are approved, including the required implementation(s).
- [ ] The sources for design decisions are recorded in the component contract and linked from the issue and Storybook docs.
- [ ] The component contract records its design properties, reuses tokens where appropriate, and keeps component-specific values in the contract; any token changes follow the Naming and Contributing guidance.
- [ ] Every in-scope implementation is complete, with API differences and out-of-scope implementations documented.
- [ ] Storybook has useful states and variants using shared args, a working implementation selector where applicable, a truthful **Code** panel, and a design-source link.
- [ ] Accessibility, responsive behavior, and the target platform have been checked; results and any known limitations are recorded.
- [ ] Relevant builds, lint, and tests pass, and the pull request has a preview and the required maintainer review.

## Adding an implementation package

Before adding a library, agree on its audience and verification target. A package may appear in Storybook as a preview before its platform checks are complete, but label that status clearly; do not offer it as a supported implementation until the target-platform verification passes.

- [ ] Add a package README with **What it is / Best for**, **Install / use**, **How it consumes design tokens**, **Contribute to it**, and **Verification**.
- [ ] Register the package with an `azDesign.library` manifest in its `package.json` and a `./storybook` adapter export, as the [library addon's README](https://github.com/az-digital/design/blob/main/packages/storybook-addon-libraries/README.md) describes. Storybook then lists it in the **Library** toolbar and the Components Overview; nothing else is registered by hand.
- [ ] Add the component to the adapter and its `lib:<key>` tag to the component's story file, so the **Code** panel shows that library's real usage. `npm run test:storybook` checks that every tag has an adapter component.
- [ ] Add package build and lint scripts and wire its build into the root `build:all` command.
- [ ] Add or update its entry in `.github/CODEOWNERS` as described in [issue #12](https://github.com/az-digital/design/issues/12).
- [ ] Agree on release and versioning before publishing; track the repository-wide approach in [issue #50](https://github.com/az-digital/design/issues/50).
- [ ] Update `.claude/skills/design-system-component/SKILL.md` to link to the human docs and package README without duplicating their conventions.
- [ ] Verify the package on its target platform, not only in Storybook; document any remaining platform checks and limitations.

# Toolkits and campaigns

This page defines the difference between university toolkits and campaigns and clarifies how those resources relate to the core design system.

## Key definitions

- Toolkit: outside the core design system but used to support university communications and product work
- Campaign: a structured effort within the design system or a defined campaign system with its own lifecycle
- Design system: the shared, reusable set of standards and patterns for digital work
